# Phase C6 — Historical Content Engine: архитектура

## Общая схема

Historical Content Engine — опциональный информационный слой поверх существующего
каталога. Он не влияет на маршрутизацию, MapKit, GPS-защиты, бюджеты времени и
Scenic Walk: ни один модуль C2–C5 не зависит от исторического контента.

```
app/db/place_history.json        ← редакторский версионированный набор (35 карточек)
        │  читается ОДИН раз за процесс
        ▼
app/db/place_history.py          ← кешированный загрузчик + валидация (fail-fast)
        │  index: catalog_key → HistoricalPlaceContent
        ▼
app/schemas/place_history.py     ← строгая Pydantic-граница (длины, URL, даты, ссылки)
        │
        ▼
app/api/v1/endpoints/places.py   ← GET /places/{place_id}/history
        │  { placeId, catalogKey, history | null }
        ▼
frontend PlacesRepository.getPlaceHistory(placeId)
        ▼
frontend HistoricalContentProvider       ← ленивый кеш на сессию, negative cache,
        │                                   per-place токены (защита от устаревших ответов)
        ▼
UI: PlaceDetailScreen (полные секции) · RouteDetailsSheet (краткая строка + «Подробнее»)
    SmartWalkWizardSheet (краткая фраза в предпросмотре) · LiveNavigationSheet
    (кнопка «Краткая история» у следующей остановки, неблокирующий bottom sheet)
```

## Ключевые решения

1. **Стабильная идентичность.** Карточки индексируются по `catalog_key` стартового
   каталога, а не по числовому `Place.id`: идентификаторы БД могут отличаться
   между установками (§4 ТЗ).
2. **Отдельное хранилище.** SQLite-схема не изменилась: исторический контент —
   редакторский файл, аналогичный `seed_places.json`, а не пользовательские
   строки в БД. Число POI (173), координаты, категории и время осмотра не
   тронуты (покрыто тестами).
3. **Опциональность.** Отсутствующая карточка = честный `history: null` в API и
   отсутствие секций в UI. Никаких «История не найдена» там, где достаточно
   обычного описания. *Невалидный* набор, напротив, отвергается при загрузке
   (fail-fast): редакторские данные поставляются вместе с приложением.
4. **Отдельный endpoint.** `GET /places/{place_id}/history` вместо раздувания
   `PlaceDetail`: список `/places` остаётся компактным, большие тексты не
   передаются в каждом листовом ответе, прежние клиенты не затронуты.
5. **Нет сетевых обращений.** Выдача карточки — только чтение из кеша файла;
   URLs источников открываются клиентом внешним браузером, содержимое страниц
   приложением не загружается (проверено тестом на перехват socket.connect).
6. **Подготовка к C13/C14.** У каждого факта/события/персоны устойчивый `id`
   (`{catalog_key}-f1`, `-t1`, …), категория, прямые ссылки на источники,
   `editorialStatus`, `lastVerifiedOn`, `contentVersion` — всё структурировано
   для будущего поиска с цитированием и адаптации текста под озвучивание.

## Инварианты регрессии (§17)

- 173 POI / 13 районов и 187 Scenic Features не изменены.
- Smart Walk v2, обычные и живописные маршруты, бюджеты 60/120/240 — без изменений.
- C4 Guidance, Camera Follow, симулятор C4.1, GPS jump safeguards, off-route
  detection, reroute — не затронуты (исторический слой читает только заголовок
  остановки и `RoutingProvider.walkPlaces`).
- Открытие истории во время навигации не останавливает сессию (провайдеры
  приложения-scoped) и не создаёт ложных событий прибытия.
